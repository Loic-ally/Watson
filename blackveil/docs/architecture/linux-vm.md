# Disposable Linux VM boundary

The Linux lab runs as a QEMU process inside the unprivileged
`aether-linux-vm` Compose service. On this ARM64 development host it boots a
Debian 13 ARM64 cloud image under QEMU TCG. The image is checked against the
committed SHA-512 manifest before it enters the VM container image. The current
Debian build is `20261026-2643`.

QEMU uses user-mode NAT. Guest traffic can reach the QEMU container's internal
`lab` interface and its API/worker peers, but the VM container has no route to
the public network. QEMU forwards guest SSH and the agent HTTP port to the VM
container; those ports exist on the private `blackveil_lab_internal` network,
and Compose publishes neither to the host. The VM container has no devices,
privileged mode, Docker socket or host path mounts. Its writable disk and
operator key live in Docker-managed named volumes.

The API and worker join the internal `lab` network for the authenticated
browser terminal and worker-to-agent jobs. The gateway and web app do not join
it. The terminal is a same-origin WebSocket on the API and is accepted
only for a server-validated `system_admin` session. The API reaches the guest's
restricted SSH account; its SSH key is read from a read-only named-volume mount
and is never sent to the browser. The per-guest SSH host key is pinned from its
public key in that same volume. The player-facing network still exposes only
gateway TCP 443.

The VM wrapper waits for `cloud-init status --wait` through its local QEMU SSH
forward before collecting the final ED25519 public host key. This bootstrap
connection trusts the guest on the wrapper's loopback port; browser sessions
always verify the saved key. Health requires both completed bootstrap and the
agent response, preventing an early SSH key from being pinned before cloud-init
replaces it.

The guest starts with a key-only, non-sudo `operator` account and a separate
Rust `aether-agent` systemd service. The guest is a Debian 13 generic-cloud
image supplied by the Debian Cloud team; its cloud-init seed is generated at VM
startup and contains no host files. See [Debian cloud image documentation](https://wiki.debian.org/Cloud)
and [QEMU user-mode networking](https://www.qemu.org/docs/master/system/qemu-manpage.html).

## Lifecycle

```sh
cd blackveil
make vm-up       # launch the challenge-mode guest
make vm-shell    # organizer shell access through the internal QEMU forward
make vm-verify   # verify challenge and patched agent behavior
make vm-reset    # remove only the two VM state volumes
```

`make vm-verify` starts an additional patched guest, exercises the same signed
envelope against both modes, and stops the patched guest after verification.
The challenge guest remains running. The operator SSH key and guest disk are
regenerated by `make vm-reset`.

New workspace users have the ordinary `operator` role and receive HTTP 403 from
the terminal route. The earlier identity stages that grant the `system_admin`
milestone have not been implemented yet, so the browser terminal is an integrated
gate awaiting those stages.
